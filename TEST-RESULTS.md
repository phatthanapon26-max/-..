# Freshy Water 8.5.0 validation

Run `npm run build` and `npm test`.

- Staff access hours: admin-only settings tab, enable/disable and daily start/end times in Asia/Bangkok. Start is inclusive, end is exclusive, overnight windows cross midnight, equal start/end and malformed settings are rejected. The default remains unrestricted until an admin saves an enabled policy.
- PostgreSQL boundary checks match the frontend to the millisecond immediately before closing. A closed staff window rejects reads, writes, payment actions and customer-code reservations. Admin access remains available, staff cannot change the schedule, anonymous status reads and direct access to the private identity helper are denied. The policy-status RPC returns only schedule/permission/server time, including while closed.
- The targeted migration is repeatable and preserves an exact fingerprint of all stored values. It changes only functions/validation trigger; it neither enables hours nor updates business records. Production migration was executed in Supabase SQL Editor on 2026-10-13. All four existing function body checksums matched the expected release before installation; the guarded transaction returned ACCESS_HOURS_INSTALLED_DATA_UNCHANGED. Existing time restrictions were not enabled automatically. Live SQL verification confirmed authenticated status access, denial for anonymous callers and the private identity helper, opening-inclusive/closing-exclusive checks, hours disabled by default, and the same stored-value fingerprint before and after. The live REST endpoint returned 401/42501 for an anonymous caller after schema reload.
- Client expiry hides the app behind an opaque lock screen. Draft form fields, mutation journal and payment command queue are preserved. Staff cached startup awaits the lightweight server policy-status RPC before showing cached data; admins retain their existing cached startup. Server clock is excluded from snapshot comparisons, so changing clock values do not rebuild unchanged views or write snapshots. Unrelated local changes made while saving settings are rebased rather than discarded.


- Mobile debtor scrolling: a fixture with 40 customers and 1,800 debts now creates 10 customer cards and at most 100 debt rows per page, versus 30 cards and 1,350 rows before this change. Each customer has ten rows per table page; scoped table updates retain the other cards. All 45 debts for a customer remain reachable, pay-all includes hidden rows, subtotal includes every row, and the full report retains all 1,800 debts. Desktop customer pagination remains 30 cards.
- Remote view replacement waits until 250 ms after scroll/touch/wheel activity ends; data synchronization still proceeds. A fixture verifies continued touch scrolling extends this delay and the updated total appears after scrolling stops. Visible debtor card position is restored after refresh when it remains in the current page. Scroll listeners do no DOM writes or layout reads.
- Live browser inspection identified a viewport-height body with its own vertical scroll (body scrollHeight 1,591 px versus clientHeight 936 px while the root remained 936 px). Screen layout now removes the fixed body height and implicit vertical overflow, leaving scrolling to the document root; horizontal clipping does not create another vertical scroller. Print rules remain unchanged.
- Debtor cards retain measured heights instead of replacing offscreen tables with estimated heights. Debtor column headers use static positioning. Mobile debtor card and action shadows/animations are removed while preserving the existing colors and full A4 report styling. These checks bound layout work; they do not measure FPS on the user's Android device.

- Print regression uses the actual report HTML and shared print CSS: 90 debts for one customer, all 90 row numbers exactly once, repeated customer/column headings, subtotal, overall total and four signatures. Saved snapshots retain exactly seven columns. Twelve customers with five debts each keep every short customer table on one page. Both A4 HTML/CSS samples and the server PDF contain five pages; Poppler renders were inspected for Thai text, numeric columns, margins and the final signature block. HTML print pagination was rendered with WeasyPrint; this is not a claim of testing every physical printer.
- Root print containers reset viewport heights, overflow and hidden application chrome so the document can continue to subsequent A4 pages. Shared report typography, centered heading, page numbering and two-by-two signatures apply to debtor reports and saved QR documents; the server PDF also uses larger debtor text and two-by-two signatures.
- Twenty concurrent synchronization reads share one request across asynchronous preflight, then release the lock for a later read. Identical remote snapshots skip reconciliation and storage work when no journal or conflict is pending. Bangkok date and number formatters are reused, including the current-day cache, rather than recreated for each row. Realtime notifications remain active; fallback polling runs every 15 seconds. These tests verify request/DOM behavior, not smoothness on the user's device.

- Performance regression in the actual app inside JSDOM: 20 identical remote receipts with 1,000 customers retain page and navigation DOM, retain existing SVG icons, and produce zero localStorage writes. Before the fix, the small demo fixture replaced page and theme icon nodes and wrote localStorage 60 times across 20 identical receipts (905 ms in one local run, versus 65 ms after the fix). These are local JavaScript/DOM measurements, not device FPS claims.
- Rapid Thai customer search renders once after typing settles, preserving caret selection and focus. Navigating while a search timer is pending keeps the selected page. New remote payment approvals still update history and notify the receiver; open forms keep their draft until closed. Compact cached snapshots plus separate journals restore unsent customer edits, preserve edits across remote reads, and refresh changed recorder names.
- Fixed chrome and cards use no backdrop blur, while preserving the existing colored surfaces and shadows. Offscreen payment/review cards defer paint; print media restores normal rendering. Touch devices disable hover transforms.


- Payment workflow on isolated PostgreSQL: all members see every operational row; staff personnel/settings secrets stay private; migration preserves the complete data fingerprint; server stamps receiver/reviewer; staff receipt and approval request commit atomically; individual approval/rejection; mandatory cancellation reasons; receiver-only pending cancellation; approved-payment undo review; legacy receipts unchanged; anonymous and generic status-forging rejected.
- Receipt recovery uses the actual production client queue against PostgreSQL: response lost after commit, client restart, retry without a second receipt/request/audit entry; simultaneous receivers result in one success; a stale row rolls back an entire bulk operation.
- Staff/admin DOM history tests: staff immediately sees pending receipts and can cancel with a reason; admin history excludes pending receipts and includes them after approval; reviewer details appear; daily-report totals exclude pending amounts and expose a separate pending count/total.

- Existing real flush loop: 10 queued records, lost successful response, safe retry, no duplicate IDs, exact old settings baseline, PT409 conflict handling.
- UI workflows in a simulated DOM: debtor validation and continuation, Enter/Backspace behavior, village codes, unique employee controls, profile file picker, CSV exports, theme switching, QR print choice, demo-only reset preserving settings and 1,000 unmarked real-style records.
- Pagination: 1,000 customer groups produce 30 rendered cards per page; searching and export use the entire filtered dataset.
- Reports: 1,000 customer tables keep each customer's rows and subtotal together, including multiple debts for one customer, and preserve overall totals. QR choices are enabled by default.
- Server tests with mocked database and mail transport: opaque document tokens, authenticated document creation through the existing RPC when no service key is configured, rejection of anonymous and other-staff private document reads, preservation of customer table titles, legacy public documents, saved SMTP settings with TLS, normalized and deduplicated group recipients, admin-only paginated backups, recipient permissions, action toggles, report deduplication, Thai dates, white-paper PDF generation.
- Formal email tests verify an actual PDF attachment, normalized group recipients, server-authoritative business/author, and prevention of sending invalid reports. Simple alerts have no PDF. PDF samples and the 90-row report are rendered with Poppler for layout inspection. No real mail is sent.
- Saved-document DOM tests verify authenticated access, customer captions, merged total cells, signatures, QR rendering and printing without issuing a new document.
- Audit tests verify employee filtering (including former employees), pagination and access to records older than the latest 200.
- Build produces updated standalone HTML and dist assets from the same sources; no production seed upload or database deletion is part of deployment.

These tests do not establish delivery to a real Gmail inbox or authenticated synchronization between two production devices. Those require the real account and server configuration. They are not a guarantee of zero defects.

Final save/scroll regression: concurrent local edits during the access-hours read are retained and flushed before the settings update. Scroll deferral also waits for an event-loop turn when reconciliation outlasts the quiet interval, so queued touch/scroll events can extend it.
